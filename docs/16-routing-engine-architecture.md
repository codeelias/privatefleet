# 16 - Routing engine architecture (analysis)

This document analyses how the fleet map should produce and validate route
geometry, and what is deliberately deferred. It is the reference for the
Phase 5 routing work and for the current demo fixtures.

## 16.1 The problem
A map renderer can draw any line. A fleet operator needs a **legal road
path**, in the **approved stop order**, that agrees with the **assignment
state** shown on the board. Three failure modes must be impossible:

1. A straight line presented as a road route.
2. Geometry drawn for an order the dispatcher never approved.
3. A failure disguised as a valid route (fallback line).

## 16.2 Options considered

| Option | What it proves | Cost / risk | Verdict |
|---|---|---|---|
| A. Straight lines between stops | Nothing about roads | Misleading | Rejected |
| B. Precomputed OSRM geometry fixtures (current demo) | UI rendering, simulator, selection, validation wiring, offline pitch | Static; must cover every scenario; must stay labelled demo | **Adopted for demo/dev** |
| C. Live OSRM Route per request | Road-following geometry from the engine | Needs routing service + failure handling; no stop sequencing | Interim step (Phase 5, Milestone 1) |
| D. OSRM Table + VROOM + OSRM Route + versioned publish | Full legal routing + constrained sequencing + reproducibility | Two services, matrix sizes, versioning, more tests | **Production target (Phase 5)** |
| E. Custom road graph shortest path | Full control | Re-implementing CH/MLD is out of scope | Rejected |

## 16.3 The production pipeline (Phase 5 target)
Stage 1 - validate state: vehicle positions, stop coordinates, assignments,
priorities, time windows, pickup-before-delivery dependencies.

Stage 2 - build the road-cost matrix: OSRM `/table` with
`annotations=duration,distance` over all eligible stops. Directed and
asymmetric by construction.

Stage 3 - optimise assignments: VROOM solves VRPTW with hard constraints
(capacity, availability, time windows, capabilities, pickup/delivery). The
objective is

```
min ( sum_ij c_ij x_ijk + lambda_L * L + lambda_U * U + lambda_R * R )
```

where `L` is lateness, `U` unassigned work, `R` disruption to existing
assignments. Hard constraints are never traded for small savings; infeasible
or unassigned jobs are returned explicitly for dispatcher review.

Stage 4 - reconstruct and validate geometry: feed VROOM's exact ordered stop
sequence back to OSRM `/route?overview=full&geometries=geojson&steps=true`.
VROOM output is not sufficient proof of the drawn shape.

Stage 5 - publish a versioned route: persist geometry, stop sequence, ETAs
and a route version atomically; broadcast `route.published`. A stale proposal
(assignments changed since Stage 1) is rejected, never applied silently.

Pseudocode (adapt to Fastify/contracts/repositories, not drop-in code):

```
buildRouteProposal(input):
  state = loadConsistentDispatchState(input)
  validateCoordinates(state); validateAssignments(state)
  matrix = osrm.table(state.locations, ["duration", "distance"])
  validateCostMatrix(matrix)
  proposal = vroom.solve(state.vehicles, state.jobs, state.shipments, matrix)
  validateOptimisationResult(proposal, state)
  candidates = for route in proposal.routes:
     stops = resolveOrderedStops(route, state)
     geometry = osrm.route([route.start, ...stops, route.end], full, geojson)
     validateRouteGeometry(geometry, route, stops)
     yield { route, stops, geometry }
  return persistRouteProposal(calculateEtasAndValidate(candidates, state))
```

## 16.4 Validation invariants (must be enforced in code)
- Coordinates finite, in range, `[longitude, latitude]` order.
- Valid `LineString` with >= 2 positions.
- Origin/destination consistency with snapped engine waypoints
  (location-sensitive tolerance, not a single global threshold).
- Ordered stop sequence preserved, including pickup/delivery dependencies.
- ETA legs consistent with route durations and service/wait time.
- One immutable version links geometry, stops, ETAs and assignment.
- Typed failures: no route, invalid geometry, stale proposal; the previously
  published route stays visible.

## 16.5 Demo fixtures (current state)
`apps/api/src/modules/demo/route-geometry.ts` holds OSRM-derived circuits
keyed by scenario and vehicle. Each circuit starts at the driver position and
visits the scenario's assigned pickups and dropoffs in order, then returns.
Fixtures are generated by `apps/api/src/db/fetch-route-geometry.ts` and are
explicitly demo data. They prove rendering, selection, movement, validation
and scenario consistency - not live engine integration.

Tolerances for fixture assertions (exact source coordinates, no geocoding):

| Assertion | Tolerance |
|---|---|
| Route origin vs vehicle position | 150 m |
| Stop vs its route leg (fixture coordinates) | 120 m |
| Movement distance vs configured speed | 0.5x - 2.0x expected |

Production tolerances will come from the routing engine's snap distances and
address accuracy, recorded per location; a hospital entrance and a rural
access road may differ.

## 16.6 GPS tracking is a different algorithm
Planned geometry is not actual movement. Raw GPS is noisy; markers follow
accepted observations and may legitimately leave the planned line. For
matching, Hidden Markov Model + Viterbi:

```
p(z_t | r_t) proportional to exp( - d(z_t, r_t)^2 / (2 * sigma_t^2) )
```

- emission likelihood from observation-to-road distance and accuracy,
- transition likelihood penalising implausible network travel,
- Viterbi for the most likely road sequence,
- low-confidence matches are rejected/marked, not force-snapped,
- raw observations are stored separately from matched results (inference is
  not measurement).

Phase 5: OSRM Match initially; Valhalla Meili only if its configuration is
needed. Never move a marker artificially along the planned route and call it
GPS.

## 16.7 Industry acceptance gate (Phase 5)
| Test | Pass condition |
|---|---|
| Coordinate order | Known London coordinates land in expected positions |
| Routing | Successful response is valid road-following geometry |
| Stop order | Geometry and ETAs correspond to the ordered waypoints |
| Optimisation | Hard constraints respected; infeasible work reported |
| Route update | Only the intended vehicle's published version changes |
| GPS | Duplicate/stale/low-confidence observations cannot corrupt state |
| Failure | Router outage/no-route/malformed geometry never yields a false line |
| Multi-tenant | Geometry and positions never cross tenant boundaries |

Measure real routing latency, failure rate, map-update delay and GPS freshness
on the pilot workload before promising numbers.

## 16.8 Sequencing
1. Demo fixtures + strict validation (this slice) - renderer, selection,
   movement, scenario consistency.
2. Phase 5 Milestone 1: OSRM Route -> verified MapLibre line (live).
3. Milestone 2: OSRM Table + VROOM -> ordered proposal.
4. Milestone 3: reconstruction + versioning + ETA propagation.
5. Milestone 4: GPS ingestion + map matching, distinct layers.
